# Week 01. 시간복잡도(Big-O) & 배열/문자열 워밍업

## 1. 왜 필요한가?

코딩테스트에서 가장 억울한 순간은 "논리는 맞는데 시간초과(TLE)"가 뜨는 경우야.
정답 로직을 짰는데도 떨어지는 이유는 대부분 하나, **입력 크기를 고려하지 않고 비효율적인 방법을 썼기 때문**이야.

비유를 들어보자. 전화번호부(이름순 정렬된 종이 책)에서 "김철수"를 찾는다고 하면:

- **완전탐색(Brute Force)**: 1페이지부터 한 장씩 넘기면서 다 찾아본다. 사람이 10명이면 금방 찾지만, 100만 명이면 하루 종일 걸릴 수도 있다.
- **이분탐색(Binary Search)**: 책이 이름순으로 정렬돼 있다는 걸 이용해서, 중간을 펼치고 "김철수보다 앞인가 뒤인가"를 보고 절반씩 버려가며 찾는다. 100만 명이어도 20번 안쪽으로 찾는다.

같은 문제를 풀어도 **어떤 방법을 쓰느냐에 따라 걸리는 시간이 천지차이**다. 코딩테스트는 보통 "입력 크기가 이만큼일 때, 1~2초 안에 답을 내라"는 제한이 있기 때문에, 내가 짠 코드가 이 제한 안에 들어올지를 미리 가늠하는 능력이 필요해. 그 가늠자가 바로 **시간복잡도(Big-O)**야.

## 2. 핵심 개념

### Big-O란?

입력 크기 `n`이 커질 때, 연산 횟수가 **얼마나 빠르게 늘어나는지**를 나타내는 표기법이야. 정확한 초 단위 시간이 아니라 "증가하는 추세"만 본다는 게 포인트.

자주 보는 것들을 느린 순 → 빠른 순으로 정리하면:

| Big-O | 이름 | 비유 |
|---|---|---|
| O(n!) | 팩토리얼 | 모든 순서(순열)를 다 따져보기 |
| O(2ⁿ) | 지수 | 선택지마다 "한다/안한다"를 다 분기해서 다 시도 |
| O(n²) | 이차 | 반 학생 전원이 서로 한 번씩 악수 (이중 for문) |
| O(n log n) | 선형로그 | 정렬. 절반씩 쪼개면서 전체를 훑는 느낌 |
| O(n) | 선형 | 책 맨 앞부터 한 장씩 넘기며 확인 |
| O(log n) | 로그 | 정렬된 책에서 이분탐색 |
| O(1) | 상수 | 배열의 인덱스로 바로 접근, 딕셔너리 조회 |

### 시간복잡도를 구하는 감

- **for문 1개** → 보통 O(n)
- **for문 안에 for문 (중첩)** → 보통 O(n²)
- **매번 절반씩 줄어드는 구조 (이분탐색, 정렬)** → O(log n) 또는 O(n log n)
- **딕셔너리/set에 접근·저장** → O(1) (배열에서 `in`으로 찾는 O(n)과 헷갈리지 말기!)

### 코딩테스트 제한시간과 입력 크기 감 잡기

프로그래머스나 백준은 보통 1초에 대략 **1억(10^8) 번 연산** 정도를 처리한다고 가정하고 문제를 낸다고 생각하면 편해. 그래서:

| 입력 크기 n | 허용되는 시간복잡도 |
|---|---|
| n ≤ 10~11 | O(n!), O(2ⁿ) 같은 완전탐색도 가능 |
| n ≤ 1,000 | O(n²), O(n³)도 웬만하면 통과 |
| n ≤ 100,000 | O(n log n)까지 |
| n ≤ 10,000,000 | O(n) 정도만 통과 |

문제를 읽으면 **가장 먼저 입력 크기(n의 범위)를 확인**하는 습관을 들이자. "n ≤ 100,000"인데 이중 for문을 짜려고 하면, 그건 이미 위험 신호야.

## 3. 코드 예제

같은 문제 "배열에서 특정 값이 존재하는지 찾기"를 시간복잡도별로 비교해보자.

```python
# O(n) - 배열을 처음부터 끝까지 순서대로 확인
def contains_linear(arr, target):
    for x in arr:          # n번 반복
        if x == target:
            return True
    return False


# O(log n) - 정렬된 배열에서 이분탐색
def contains_binary(sorted_arr, target):
    left, right = 0, len(sorted_arr) - 1
    while left <= right:               # 매번 절반씩 줄어듦 → log n번
        mid = (left + right) // 2
        if sorted_arr[mid] == target:
            return True
        elif sorted_arr[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return False


# O(1) - set/dict을 미리 만들어두면 조회는 상수 시간
def contains_hash(arr, target):
    lookup = set(arr)      # 이 변환 자체는 O(n), 한 번만 하면 됨
    return target in lookup   # 조회는 O(1)
```

그리고 "흔히 실수하는 O(n²)" 예시:

```python
# 두 배열에서 공통 원소 찾기 - 나쁜 예 (O(n * m))
def common_bad(a, b):
    result = []
    for x in a:
        for y in b:          # a의 원소 하나마다 b 전체를 또 순회
            if x == y:
                result.append(x)
    return result


# 좋은 예 (O(n + m)) - set을 이용해서 이중 반복을 없앤다
def common_good(a, b):
    b_set = set(b)
    return [x for x in a if x in b_set]
```

핵심은 "반복문 안에 또 반복문 + `in` 연산이 배열에 걸려 있으면" 시간복잡도가 폭발하기 쉽다는 것. 이럴 때 `set`이나 `dict`로 바꿀 수 없는지 항상 의심해보자 (이건 week06 해시맵에서 더 깊게 다룰 거야).

## 4. 감으로 익히는 기준표

문제를 풀기 전에 아래 표로 "이 정도 복잡도면 되겠다"는 감을 빠르게 잡는 연습을 하자.

| n의 범위 | 대략 이 정도까지 시도 가능 | 대표 접근 |
|---|---|---|
| n ≤ 10 | 완전탐색, 순열/조합 다 시도 | 재귀, 브루트포스 |
| n ≤ 1,000 | O(n²) 이중 for문 | 브루트포스, 간단한 DP |
| n ≤ 100,000 | O(n log n) | 정렬, 이분탐색, 우선순위 큐 |
| n ≤ 1,000,000 | O(n) | 한 번 순회, 투 포인터, 해시맵 |
